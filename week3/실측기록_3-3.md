## 3-3 실측 기록 (본인 환경)
 
| 항목 | CSV | Parquet(zstd) | 배율 |
|---|---|---|---|
| 파일 크기 |  40.6MB |  9.8MB | 4.1배 |
| 집계 질의 |  0.155초 |  0.004초 | 35.4배 |
| 한 열만 읽기 |  0.133초 |  0.0024초 | — |
| 다섯 열 읽기 |  0.186초 |  0.0200초 | — |
압축 방식 비교: zstd  9.8MB / snappy  15.9MB / gzip  10.6MB
 
거꾸로 나온 측정: count(*) 로 잰 「전부 읽기」가 더 빨랐던 이유 —

겉보기에는 전체 컬럼을 읽은 다음 행 개수를 세는 것처럼 보입니다.
하지만 DuckDB는 SQL을 최적화하기 때문에 내부의 SELECT * 에서 모든 컬럼 값을 가져올 필요가 없다고 판단합니다.
Parquet 파일에는 전체 행 개수 등의 메타데이터가 저장되어 있습니다.
따라서 DuckDB는 count(*)를 처리할 때 실제 데이터 전체를 읽지 않고 Parquet 메타데이터만 활용할 수 있습니다.


 
결론: (한 문장으로 — 왜 중간 산출물을 Parquet로 두는가)
데이터 저장 공간을 줄이고, 이후 분석에서 필요한 데이터만 빠르게 읽어 재사용하기 위해서입니다.
